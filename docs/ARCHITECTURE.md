# Hybrid C++/Python Limit Order Book Simulator

# Chapter 1–7 — Order Book, Matching Engine, Order Tracking, Modification, Event-Driven Simulation, Market Microstructure Metrics & Execution Analysis

## 1. Overview

This project is a hybrid C++/Python limit order book simulator designed to model financial market microstructure.

Chapter 1 establishes the fundamental data model of the limit order book. It implements orders, price levels, bid and ask sides, best-price queries, spread calculation, and order cancellation.

Chapter 2 extends this foundation with a matching engine capable of processing crossing orders and generating trades according to price-time priority.

Chapter 3 introduces fast order-ID tracking through an auxiliary hash map. This allows the order book to locate a resting order using its `OrderId` without scanning every price level and order.

Chapter 4 introduces order modification and replace semantics. Orders can have their quantity or price changed while preserving market-matching rules such as FIFO priority. Modifications that change an order's queue priority are implemented through cancellation followed by reinsertion.

Chapter 5 introduces an event-driven simulation layer. Market actions are represented as timestamped and sequenced events, and a `Simulator` processes those events through the existing `OrderBook`. The simulator provides deterministic event processing, chronological validation, sequence-number validation, event storage, and trade-history collection.

Chapter 6 introduces a read-only market microstructure metrics layer. This layer derives observable quantities from the existing `OrderBook` and simulator trade history without duplicating market state or mutating the underlying engine. It provides top-of-book metrics, depth, imbalance, and basic trade statistics.

Chapter 7 introduces execution analysis. It analyzes the trades generated by the matching engine on a per-incoming-order basis and measures executed quantity, execution value, VWAP, arrival-price slippage, execution cost, and liquidity consumed. The execution layer reuses the existing Chapter 6 midpoint calculation and does not duplicate market-state logic.

The implementation prioritizes:

```text
correctness
    ↓
explicit architecture
    ↓
state invariants
    ↓
testing
    ↓
realistic simulation
    ↓
measurement
    ↓
performance optimization
    ↓
research
```

The current architecture is:

```text

                    Engine
```

# Part I — Core Order Book

## 2. Core Data Model

### 2.1 Order

An `Order` represents a single order submitted to the market.

Each order contains:

* `OrderId` — unique identifier for the order
* `Side` — `BUY` or `SELL`
* `Price` — integer price representation
* `Quantity` — number of units currently remaining

Conceptually:

```text
Order

├── ID
├── Side
├── Price
└── Quantity
```

For example:

```text
Order ID: 10
Side:     BUY
Price:    8150
Quantity: 200
```

The order represents a request to buy 200 units at a price of 8150 ticks.

During matching, `Quantity` represents the order's remaining unfilled quantity.

---

## 3. Integer Price Representation

Prices are represented using integers rather than floating-point values.

For example:

```text
$100.00 → 10000
$100.25 → 10025
$105.50 → 10550
```

This avoids floating-point precision problems.

The project therefore defines:

```cpp
using Price = std::int64_t;
```

Using integer ticks also provides a cleaner foundation for later high-performance market simulation.

The integer representation remains the canonical representation of quoted prices throughout the architecture.

Floating-point values are introduced only where a derived metric naturally requires them, such as:

```text
mid-price
relative spread
order-book imbalance
VWAP
slippage
```

---

## 4. Price Level

A `PriceLevel` represents all orders currently resting at the same price on the same side of the book.

Each price level contains:

```text
PriceLevel

├── price
├── orders
└── total_quantity
```

For example:

```text
Order 1 → BUY @ 8000 → 100
Order 6 → BUY @ 8000 → 130
```

they belong to the same price level:

```text
Price: 8000

Orders:
    Order 1 → 100
    Order 6 → 130

Total Quantity: 230
```

The individual orders remain separate because they have different order IDs, while the price level provides an aggregate view of liquidity at that price.

The order sequence inside a price level is significant because it represents FIFO priority.

---

## 5. Order Book

The `OrderBook` contains two independent sides:

```text
OrderBook

├── bids
├── asks
└── order_map
```

### Bids

Bids represent BUY orders.

Buyers prefer lower prices, but the market prioritizes the highest available bid.

Therefore:

```text
8150
8000
7950
7800
```

has:

```text
Best Bid = 8150
```

### Asks

Asks represent SELL orders.

Sellers prefer higher prices, but the market prioritizes the lowest available ask.

Therefore:

```text
8050
8100
8350
```

has:

```text
Best Ask = 8050
```

The best prices represent the immediately available top of the order book.

---

## 6. Best Bid and Best Ask

The order book exposes two queries:

```cpp
Price best_bid();
Price best_ask();
```

`best_bid()` returns the highest available BUY price.

`best_ask()` returns the lowest available SELL price.

The current empty-book convention is:

```text
No bid → best_bid() returns 0
No ask → best_ask() returns 0
```

Within the simulator, `0` is reserved as a sentinel for the absence of an available quote and is not used as a valid market price.

This convention was retained rather than introducing `std::optional<Price>` because changing the core representation would unnecessarily propagate through the existing architecture.

---

## 7. Bid-Ask Spread

The bid-ask spread measures the price difference between the best ask and best bid.

The formula is:

```text
Spread = Best Ask − Best Bid
```

For example:

```text
Best Bid = 8050
Best Ask = 8100

Spread = 8100 − 8050
       = 50 ticks
```

The spread is calculated from the current top of book.

When either side is unavailable, the existing `OrderBook` convention returns:

```text
Spread = 0
```

---

## 8. Adding an Order

When an order is added, the order book determines its side.

```text
                    Order
                      |
            +---------+---------+
            |                   |
           BUY                SELL
            |                   |
          bids                asks
```

The order is then placed into the price level corresponding to its price.

If that price level already exists, the order is appended to the existing level.

If it does not exist, a new price level is created.

Orders are stored in insertion order within a price level so that FIFO priority can be preserved by the matching engine.

---

## 9. Order Cancellation

Orders can be removed using their `OrderId`.

The current implementation uses the `OrderMap` to locate the order before removing it.

Conceptually:

```text
cancel(order_id)

      ↓

Find OrderLocation in OrderMap

      ↓

Locate corresponding PriceLevel

      ↓

Remove order from price level

      ↓

Update total_quantity

      ↓

Remove OrderMap entry

      ↓

Update shifted indices

      ↓

Is price level empty?

 ├── YES → Remove price level
 └── NO  → Keep price level
```

The operation returns `true` when an order is successfully cancelled and `false` when the order does not exist or cannot be located.

---

## 10. Empty Price Levels

A price level should not remain in the book after its final order has been removed.

The matching engine follows the same rule after execution: when the final resting order at a price level is completely filled, the empty price level is removed.

This ensures that the order book represents currently available liquidity rather than historical price levels.

---

# Part II — Matching Engine

## 11. Matching Engine Overview

Chapter 2 introduces the matching engine.

The matching engine processes an incoming order against the opposite side of the book.

The fundamental rule is:

```text
BUY  → matches against ASKS
SELL → matches against BIDS
```

The incoming order is matched only while its price crosses the current best executable price.

Conceptually:

```text
Incoming Order

      ↓

Determine Side

      ↓

Find Opposite Side

      ↓

Check Price Crossing

      ↓

Match FIFO Orders

      ↓

Generate Trade(s)

      ↓

Update Quantities

      ↓

Remove Filled Orders / Levels

      ↓

Rest Remaining Quantity
```

Matching remains the responsibility of `OrderBook`.

---

## 12. Trade

A `Trade` represents one executed transaction between an incoming order and a resting order.

The structure contains:

```text
Trade

├── incoming_order
├── resting_order
├── price
└── quantity
```

Conceptually:

```cpp
struct Trade {
    OrderId incoming_order;
    OrderId resting_order;
    Price price;
    Quantity quantity;
};
```

The order identifiers are stored as `OrderId` values rather than complete `Order` objects.

A single incoming order can therefore generate multiple `Trade` objects when it consumes liquidity from multiple resting orders.

---

## 13. BUY Matching

For an incoming BUY order, the matching engine examines the ask side.

The lowest ask has highest execution priority.

The crossing condition is:

```text
incoming BUY price >= resting ASK price
```

As long as this remains true, matching continues.

Once:

```text
incoming BUY price < resting ASK price
```

matching stops.

Any remaining quantity becomes resting bid liquidity.

---

## 14. SELL Matching

For an incoming SELL order, the matching engine examines the bid side.

The highest bid has highest execution priority.

The crossing condition is:

```text
incoming SELL price <= resting BID price
```

As long as this remains true, matching continues.

Once:

```text
incoming SELL price > resting BID price
```

matching stops.

Any remaining quantity becomes resting ask liquidity.

---

## 15. Price-Time Priority

The matching engine follows price-time priority.

Price priority determines which price level executes first.

For BUY orders:

```text
Lowest ASK first
```

For SELL orders:

```text
Highest BID first
```

Within a single price level, time priority is represented by the order sequence inside the `orders` vector.

Therefore:

```text
Price: 10000

Order 1 → 30
Order 2 → 40
```

means Order 1 has priority over Order 2.

---

## 16. Full Fill

A full fill occurs when the incoming order's remaining quantity is less than or equal to the resting order's quantity.

If the incoming quantity exactly equals the resting quantity, both become fully filled and the resting order is removed.

The matching engine reuses the normal order-removal path when a resting order has been completely consumed.

---

## 17. Partial Fill

A partial fill occurs when the incoming order is larger than the available quantity of the current resting order.

Example:

```text
Resting SELL → 30
Incoming BUY  → 50
```

The trade is:

```text
Quantity = 30
```

The resting order is completely filled and removed.

The incoming order retains:

```text
Remaining quantity = 20
```

The engine then continues searching for additional executable liquidity.

---

## 18. Multiple Price Levels

An incoming order can consume liquidity across multiple price levels.

Example:

```text
ASKS

10000 → 20
10100 → 30
10200 → 40
```

Incoming:

```text
BUY @ 10200 → 60
```

Execution becomes:

```text
20 @ 10000
30 @ 10100
10 @ 10200
```

This multi-level execution behavior becomes important for Chapter 7 execution-cost analysis.

---

## 19. Trade Generation

Each individual execution creates a `Trade` object.

A single incoming order may therefore create:

```text
Trade 1
Trade 2
Trade 3
...
```

The returned:

```cpp
std::vector<Trade>
```

preserves execution order.

---

## 20. Order Quantity During Matching

The incoming order's `Quantity` represents its remaining unfilled amount.

During execution:

```text
Initial Quantity
      ↓
Match
      ↓
Subtract Executed Quantity
      ↓
Remaining Quantity
      ↓
Continue Matching
```

When the remaining quantity reaches zero, matching stops.

If positive quantity remains after all executable liquidity has been consumed, that quantity is added to the appropriate side of the order book.

---

## 21. Matching and Book State Updates

Every execution updates both order and price-level state.

For a trade:

```text
Trade Quantity = Q
```

the resting order is reduced by:

```text
Resting Quantity -= Q
```

and the corresponding price level is reduced by:

```text
Total Quantity -= Q
```

If the resting order reaches zero, it is removed.

If that removal leaves the price level empty, the price level is also removed.

The order book therefore remains synchronized with executed trades.

---

## 22. Crossing Versus Resting

An incoming order has two possible outcomes.

### Crossing Order

```text
Incoming Order
      ↓
Executable Liquidity Exists
      ↓
Matching
      ↓
Trade(s)
```

The order may become completely filled or may retain a remaining quantity.

### Non-Crossing Order

```text
Incoming Order
      ↓
No Executable Liquidity
      ↓
No Trade
      ↓
Order Rests on Book
```

---

# Part III — Order ID Tracking

## 23. Motivation for OrderMap

Without additional indexing, finding an order by `OrderId` requires scanning bid and ask price levels and the orders stored inside them.

Chapter 3 introduces:

```text
OrderId
   ↓
OrderLocation
```

using:

```cpp
std::unordered_map<OrderId, OrderLocation>
```

The map provides average constant-time lookup under normal hash-table behavior.

The map acts as an index into the actual order-book storage rather than replacing it.

---

## 24. OrderLocation

An `OrderLocation` identifies where an order is stored inside the order book.

It contains:

```text
OrderLocation

├── side
├── price
└── index
```

Conceptually:

```cpp
struct OrderLocation {
    Side side;
    Price price;
    std::size_t index;
};
```

---

## 25. OrderMap Structure

The current `OrderMap` contains:

```cpp
std::unordered_map<OrderId, OrderLocation> orders;
```

Conceptually:

```text
OrderBook

├── bids
│   └── PriceLevels
│       └── Orders
│
├── asks
│   └── PriceLevels
│       └── Orders
│
└── OrderMap
    └── OrderId → OrderLocation
```

The actual order remains stored in its `PriceLevel`.

---

## 26. Why the Map Stores Location Rather Than Order Pointers

The current book stores orders as values inside:

```cpp
std::vector<Order>
```

The `OrderMap` therefore stores:

```text
OrderId
    ↓
Side + Price + Index
```

rather than relying on persistent pointers into vectors.

This keeps ownership simple:

```text
OrderBook
    owns PriceLevels
        which own Orders
```

The `OrderMap` remains an auxiliary lookup structure.

---

## 27. Adding Orders to OrderMap

When an order becomes resting liquidity, the `OrderBook` inserts its location into the `OrderMap`.

An incoming order that becomes completely filled during matching is never added to the `OrderMap`.

---

## 28. Removing Orders from OrderMap

When a resting order is cancelled or completely filled, its `OrderMap` entry is removed.

Because the underlying vector may shift, locations of subsequent orders may also need updating.

---

## 29. Shifted Indices

The order storage uses:

```cpp
std::vector<Order>
```

Erasing an order from the middle shifts subsequent orders one position toward the front.

Therefore the corresponding `OrderMap` locations must be synchronized.

---

## 30. OrderMap Invariant

The central invariant is:

```text
Every resting order in the book has exactly one OrderMap entry.

Every OrderMap entry corresponds to exactly one resting order.
```

This remains a fundamental system invariant.

---

## 31. Partial Fills and OrderMap

A partial fill changes quantity but not location.

Therefore:

```text
Partial Fill
    ↓
Quantity changes
    ↓
Location unchanged
    ↓
OrderMap unchanged
```

---

## 32. Full Fills and OrderMap

When a resting order is completely filled:

```text
Resting Quantity → 0
```

the order is removed from the book and its `OrderMap` entry is removed.

---

# Part IV — Order Lookup and Modification

## 33. Direct Order Lookup

Chapter 4 introduces:

```cpp
Order* find_order(OrderId order_id);
```

The lookup path is:

```text
OrderId
   ↓
OrderMap::find()
   ↓
OrderLocation
   ↓
Select bids / asks using side
   ↓
Find PriceLevel using price
   ↓
Access orders[index]
   ↓
Return Order*
```

The returned pointer is a temporary access mechanism.

It must not be retained across operations that can erase or reallocate the underlying vector.

---

## 34. Order Modification / Replace

The public modification operation is:

```cpp
bool modify(
    OrderId order_id,
    Price new_price,
    Quantity new_quantity
);
```

Its purpose is to modify a resting order while respecting FIFO rules.

Conceptually:

```text
modify()

    ↓

find_order()

    ↓

Does order exist?

 ├── NO → false
 │
 └── YES
      ↓
new_quantity == 0?
 │
 ├── YES → cancel()
 │
 └── NO
      ↓
Same price AND quantity decrease/equal?
 │
 ├── YES → modify in place
 │
 └── NO
      ↓
cancel(old)
      ↓
add(replacement)
      ↓
FIFO priority resets
```

---

## 35. FIFO Rules for Modification

The current rules are:

### Same Price + Quantity Decrease

Modify in place.

FIFO is preserved.

### Same Price + Quantity Increase

Cancel and reinsert.

FIFO is lost.

### Price Change

Cancel and reinsert.

FIFO priority resets.

---

## 36. Quantity Zero as Cancellation

A modification with:

```text
new_quantity = 0
```

is treated as cancellation.

---

## 37. Order ID and Side Preservation

When an order is replaced, the replacement retains:

```text
Original OrderId
Original Side
```

Only the modified attributes change:

```text
Price
Quantity
```

---

## 38. OrderMap During Modification

For in-place modification:

```text
Order
   ↓
Quantity updated
   ↓
Location unchanged
   ↓
OrderMap remains valid
```

For replacement:

```text
cancel()
   ↓
OrderMap entry removed
   ↓
add()
   ↓
New location created
   ↓
OrderMap entry recreated
```

# Part V — Event-Driven Market Simulation

## 39. Event Representation

Chapter 5 introduces an event abstraction above the existing order-book engine.

The event representation is defined in:

```text
cpp/include/lob/event.hpp
```

Current event types:

```cpp
enum class EventType {
    ADD,
    CANCEL,
    MODIFY
};
```

Each event contains:

```text
Event

├── type
├── timestamp
├── sequence
├── order
├── order_id
├── new_price
└── new_quantity
```

Field interpretation:

```text
ADD
→ order

CANCEL
→ order_id

MODIFY
→ order_id
→ new_price
→ new_quantity
```

---

## 40. Timestamp and Sequence Number

Each event contains:

```text
timestamp
sequence
```

`timestamp` represents logical simulation time.

`sequence` resolves ordering between multiple events occurring at the same timestamp.

The current model is:

```text
100   0
100   1
100   2

101   0
101   1

102   0
```

Rules:

```text
timestamp < current_time
    → reject

timestamp == current_time
    → sequence > last_sequence

timestamp > current_time
    → sequence == 0
```

Accepted events update:

```text
current_time
last_sequence
```

Rejected events do not advance simulator time or sequence state.

The timestamp unit is documented as logical nanoseconds for the current simulator representation.

---

## 41. Simulator

The `Simulator` contains:

```text
Simulator

├── OrderBook
├── current_time
├── last_sequence
├── events
├── trades
├── sides_by_order
└── reference_prices_by_order
```

Conceptually:

```cpp
struct Simulator {

    OrderBook order_book;

    Timestamp current_time = 0;

    Sequence last_sequence = 0;

    std::vector<Event> events;

    std::vector<Trade> trades;

    SidesByOrder sides_by_order;

    void add_event(Event event);

    void process_event(const Event& event);

    void process_events();

    ExecutionResultsByOrder calculate_execution_results();
};
```

The simulator does not replace the `OrderBook`.

It coordinates event processing and preserves information needed for later analysis.

---

## 42. Simulator Event Dispatch

### ADD

Before executing an accepted ADD event, the simulator records execution context:

```text
Incoming OrderId
        ↓
Incoming Side
        ↓
Arrival Midpoint
```

The midpoint is captured from the current book:

```cpp
calculate_mid_price(this->order_book)
```

before matching begins.

The simulator then calls:

```cpp
OrderBook::process_order()
```

and appends generated trades to:

```cpp
trades
```

### CANCEL

The simulator calls:

```cpp
OrderBook::cancel(order_id)
```

### MODIFY

The simulator calls:

```cpp
OrderBook::modify(
    order_id,
    new_price,
    new_quantity
);
```

The `OrderBook` remains responsible for book-state semantics.

---

## 43. Event Validation

Before an event modifies the order book, the simulator validates:

```text
Event
  ↓
Timestamp
  ↓
Sequence
  ↓
Event type
  ↓
Event-specific state
  ↓
Execution
  ↓
Update simulator clock
```

Rejected events do not intentionally modify the market state.

---

## 44. Event Stream

Events are stored using:

```cpp
std::vector<Event> events;
```

Events are added in insertion order.

The simulator does not automatically sort events during insertion.

Validation occurs during processing.

---

## 45. Processing an Event Stream

The simulator exposes:

```cpp
void process_events();
```

which processes stored events sequentially:

```text
events[0]
   ↓
process_event()

events[1]
   ↓
process_event()

events[2]
   ↓
process_event()

...
```

---

## 46. Simulation Clock

The simulator maintains:

```cpp
Timestamp current_time;
Sequence last_sequence;
```

These represent the temporal position of the most recently accepted event.

## 47. Duplicate Order Protection

The simulator prevents duplicate active `ADD` order IDs.

Conceptually:

```text
ADD Event
   ↓
Does OrderId already exist?

   └── NO  → Process
```

This maintains:

```text
One active resting order
    ↔
One unique OrderId
```

```cpp
std::vector<Trade> trades;
```

# Part VI — Market Microstructure Metrics



No duplicated top-of-book state is maintained.

## 54. Mid-Price

The mid-price is:

```text
Mid = (Best Bid + Best Ask) / 2
```

Because prices are integer ticks, the resulting mid-price can fall between ticks.

For example:

```text
Best Bid = 10000
Best Ask = 10501

Mid = 10250.5
```

Therefore:

```cpp
using MidPrice = double;
```

When either side is unavailable:

```text
Mid = 0.0
```

---

## 55. Absolute Spread

The absolute spread is:

```text
Spread = Best Ask − Best Bid
```

The metrics layer delegates to:

```cpp
OrderBook::spread()
```

---

## 56. Relative Spread

Relative spread normalizes the spread by the midpoint:

```text
Relative Spread
=
(Best Ask − Best Bid)
--------------------- × 100
         Mid
```

When the midpoint is unavailable:

```text
Relative Spread = 0.0
```

---

## 57. Bid Depth

Bid depth measures total resting quantity on the bid side.

The current implementation sums:

```text
total_quantity
```

across all bid price levels.

---

## 58. Ask Depth

Ask depth is calculated analogously across all ask price levels.

---

## 59. Order Book Imbalance

The normalized imbalance is:

```text
Imbalance
=
(Bid Depth − Ask Depth)
------------------------
(Bid Depth + Ask Depth)
```

The result lies conceptually in:

```text
[-1, +1]
```

When both sides have zero depth:

```text
Imbalance = 0.0
```

---

## 60. Trade Count

The current definition is:

```text
Trade Count = number of Trade objects
```

This is distinct from the number of incoming orders.

# Part VII — Execution Analysis

## 67. Execution Analysis Overview

Chapter 7 introduces an execution-analysis layer above the existing simulation engine.

Chapter 6 asks:

```text
What does the market look like?
```

Chapter 7 asks:

```text
What did a specific incoming order actually cost?
```

The execution layer analyzes the trades already generated by the matching engine.

It does not perform matching.

It does not own orders.

It does not maintain another order book.

The architecture is:

```text
Simulator
    |
    +── Trade History
    |
    +── Incoming Order Side
    |
    +── Arrival Reference Price
    |
    v
Execution Analysis
    |
    +── Executed Quantity
    +── Execution Value
    +── VWAP
    +── Slippage
    +── Execution Cost
    +── Liquidity Consumed
    |
    v

```


## 69. Execution Result

The result of analyzing one incoming order is:

```cpp
struct ExecutionResult {
    Quantity executed_quantity;
    ExecutionValue execution_value;
    Vwap execution_vwap;
    MidPrice reference_price;
    Slippage slippage;
    ExecutionCost execution_cost;
    Quantity liquidity_consumed;
};
```

The result contains no order-book ownership.

It is purely a derived value object.

---

## 70. Execution Types

The current execution-related types are:

```cpp
using Vwap = double;
using ExecutionValue = std::int64_t;
using Slippage = double;
using ExecutionCost = std::int64_t;
```

The existing basic types remain:

```cpp
Price = std::int64_t
Quantity = std::uint64_t
OrderId = std::uint64_t
```

Quoted prices remain integer ticks.

VWAP, midpoint, and slippage use floating-point representation because they can be fractional.

---

## 71. Execution Value

Execution value is:

```text
Execution Value
=
Σ (Trade Price × Trade Quantity)
```

For example:

```text
50 @ 10500
70 @ 10600
```

produces:

```text
50 × 10500 = 525000
70 × 10600 = 742000

Execution Value = 1267000
```

The resulting unit is:

```text
price ticks × quantity
```

rather than currency.

---

## 72. Executed Quantity

Total executed quantity is:

```text
Q = Σ Trade Quantity
```

For example:

```text
50 + 70 = 120
```

This is the total quantity actually filled for the incoming order.

---

## 73. VWAP

Execution VWAP is:

```text
VWAP
=
Σ(price × quantity)
-------------------
    Σ quantity
```

For example:

```text
Execution Value = 1267000
Quantity        = 120

VWAP
= 1267000 / 120
≈ 10558.3333
```

The current function is:

```cpp
Vwap calculate_VWAP(
    std::vector<Trade> trades
);
```

An empty execution returns:

```text
VWAP = 0.0
```

to avoid division by zero.

---

## 74. Arrival Reference Price

Execution quality requires a reference price.

The project uses:

```text
Arrival Midpoint
```

as the primary execution reference.

The critical timing rule is:

```text
Capture midpoint
        ↓
Before matching
        ↓
Execute incoming order
```

The reference is therefore based on the market state visible immediately before the order executes.

The execution layer does not calculate this reference itself.

Instead:

```text
Metrics Layer
    ↓
calculate_mid_price(OrderBook)
    ↓
Simulator captures result
    ↓
Execution Analysis receives reference price
```

This prevents the execution layer from accidentally using the post-execution order book.

---

The project already has:


The execution layer does **not** implement another midpoint calculation.

The responsibility split is:

```text

    Knows HOW to calculate midpoint
```

```text

    Knows WHEN to capture arrival midpoint
```

```text

```

This prevents duplicate logic.

## 78. Slippage Convention

The project uses a side-aware slippage definition relative to the arrival midpoint.

For BUY:

```text
Slippage
=
VWAP − Arrival Midpoint
```

For SELL:

```text
Slippage
=
Arrival Midpoint − VWAP
```

Therefore:

```text
Positive slippage
    → execution was less favorable than reference

Zero slippage
    → execution matched the reference

Negative slippage
    → execution was more favorable than reference
```

The sign convention is defined so that unfavorable execution produces positive slippage for both sides.

---

## 79. BUY Slippage

For a BUY order:

```text
Reference = 10250
VWAP      = 10558.3333
```

therefore:

```text
Slippage
=
10558.3333 − 10250
=
308.3333
```

---

## 80. SELL Slippage

For a SELL order:

```text
Reference = 10300
VWAP      = 10000
```

therefore:

```text
Slippage
=
10300 − 10000
=
300
```

The same positive-sign convention is preserved.

---

## 81. Execution Cost

Execution cost is defined as:

```text
Execution Cost
=
Slippage × Executed Quantity
```

For the BUY example:

```text
Slippage = 308.3333
Quantity = 120

Cost ≈ 37000
```

For the SELL example:

```text
Slippage = 300
Quantity = 80

Cost = 24000
```

The resulting unit is:

```text
price ticks × quantity
```

matching the unit of execution value.

---

## 82. Liquidity Consumed

Every filled unit in the current matching model consumes one unit of resting liquidity.

Therefore:

```text
Liquidity Consumed
=
Σ Trade Quantity
```

Numerically, this is equal to:

```text
Executed Quantity
```

However, the project intentionally keeps:

```cpp
calculate_liquidity_consumed()
```

as a distinct function.

The distinction is conceptual:

```text
Executed Quantity

    measures how much of the incoming order was filled
```

versus:

```text
Liquidity Consumed

    measures how much resting liquidity was removed
```

They happen to be equal under the current matching model.

Keeping them separate leaves room for later execution-model extensions without collapsing two different concepts into one metric.

---

## 83. Market Impact Scope

Chapter 7 does not claim a full causal market-impact model.

The current chapter measures:

```text
execution price
execution quantity
arrival midpoint
slippage
execution cost
liquidity consumed
```

Later work may measure:

```text
post-trade price movement
short-horizon price response
depth depletion
spread changes
```

but an observed post-trade movement should not automatically be interpreted as causal market impact.

A more detailed impact model is deferred to later chapters.

# Part XIV — Current Performance Model

## 119. Current Performance Model

The current vector-based implementation is designed primarily for correctness and conceptual clarity.

It is not yet the final high-performance architecture.

Current characteristics include:

```text
Price-level search
    → linear in number of levels

Order insertion into level
    → vector append

Order removal
    → vector erase + shifted-index updates

Order ID lookup
    → average O(1) through unordered_map

Direct order resolution
    → map lookup + price-level search

Matching
    → traversal of price levels and orders

FIFO-preserving modification
    → in-place mutation

Priority-changing modification
    → cancel + reinsert

Event storage
    → vector append

Event processing
    → sequential event traversal

Bid / ask depth
    → traversal of price levels

Trade count
    → O(1) from vector size

Trade volume
    → linear in trade-history length

Trade grouping
    → average O(n) over trade history

Execution result calculation
    → linear in grouped trade count

Complete execution analysis
    → dominated by trade aggregation and calculation

Complete market metrics
    → dominated by depth and trade-volume traversal
```

The metrics and execution layers do not introduce mutable caches for premature optimization.

Future optimization decisions will be measured rather than assumed.
