# Hybrid C++/Python Limit Order Book Simulator

# Chapter 1–8 — Order Book, Matching Engine, Order Tracking, Modification, Event-Driven Simulation, Market Microstructure Metrics, Execution Analysis & Inventory/P&L

## 1. Overview

This project is a hybrid C++/Python limit order book simulator designed to model financial market microstructure, execution, inventory, and portfolio accounting.

Chapter 1 establishes the fundamental data model of the limit order book. It implements orders, price levels, bid and ask sides, best-price queries, spread calculation, and order cancellation.

Chapter 2 extends this foundation with a matching engine capable of processing crossing orders and generating trades according to price-time priority.

Chapter 3 introduces fast order-ID tracking through an auxiliary hash map. This allows the order book to locate a resting order using its `OrderId` without scanning every price level and order.

Chapter 4 introduces order modification and replace semantics. Orders can have their quantity or price changed while preserving market-matching rules such as FIFO priority. Modifications that change an order's queue priority are implemented through cancellation followed by reinsertion.

Chapter 5 introduces an event-driven simulation layer. Market actions are represented as timestamped and sequenced events, and a `Simulator` processes those events through the existing `OrderBook`. The simulator provides deterministic event processing, chronological validation, sequence-number validation, event storage, and trade-history collection.

Chapter 6 introduces a read-only market microstructure metrics layer. This layer derives observable quantities from the existing `OrderBook` and simulator trade history without duplicating market state or mutating the underlying engine. It provides top-of-book metrics, depth, imbalance, and basic trade statistics.

Chapter 7 introduces execution analysis. It analyzes the trades generated by the matching engine on a per-incoming-order basis and measures executed quantity, execution value, VWAP, arrival-price slippage, execution cost, and liquidity consumed. The execution layer reuses the existing Chapter 6 midpoint calculation and does not duplicate market-state logic.

Chapter 8 introduces inventory and portfolio accounting above the execution layer. The `InventoryModel` maintains persistent position, cash, average cost basis, and realized P&L while deriving unrealized P&L, portfolio value, and inventory exposure from the current state and a supplied mark price. The simulator integrates generated trades into the inventory model while preserving the existing matching and execution architecture.

The implementation prioritizes:


# Part I — Core Order Book

## 2. Core Data Model

### 2.1 Order

An `Order` represents a single order submitted to the market.

Each order contains:

* `OrderId` — unique identifier for the order
* `Side` — `BUY` or `SELL`
* `Price` — integer price representation
* `Quantity` — number of units currently remaining

Conceptually:

```text
Order

├── ID
├── Side
├── Price
└── Quantity
```

For example:

```text
Order ID: 10
Side:     BUY
Price:    8150
Quantity: 200
```

The order represents a request to buy 200 units at a price of 8150 ticks.

During matching, `Quantity` represents the order's remaining unfilled quantity.

---

## 3. Integer Price Representation

Prices are represented using integers rather than floating-point values.

For example:

```text
$100.00 → 10000
$100.25 → 10025
$105.50 → 10550
```

This avoids floating-point precision problems.

The project therefore defines:

```cpp
using Price = std::int64_t;
```

Using integer ticks also provides a clean foundation for later high-performance market simulation.

The integer representation remains the canonical representation of quoted prices throughout the architecture.

Floating-point values are introduced only where a derived metric naturally requires them, such as:

```text
mid-price
relative spread
order-book imbalance
VWAP
slippage
average cost
P&L
```

---

## 4. Price Level

A `PriceLevel` represents all orders currently resting at the same price on the same side of the book.

Each price level contains:

```text
PriceLevel

├── price
├── orders
└── total_quantity
```

The individual orders remain separate because they have different order IDs, while the price level provides an aggregate view of liquidity at that price.

The order sequence inside a price level is significant because it represents FIFO priority.

---

## 5. Order Book

The `OrderBook` contains two independent sides:

```text
OrderBook

├── bids
├── asks
└── order_map
```

Bids represent BUY orders.

Asks represent SELL orders.

The best bid is the highest available BUY price.

The best ask is the lowest available SELL price.

The best prices represent the immediately available top of the order book.

---

## 6. Best Bid and Best Ask

The order book exposes:

```cpp
Price best_bid();
Price best_ask();
```

`best_bid()` returns the highest available BUY price.

`best_ask()` returns the lowest available SELL price.

The current empty-book convention is:

```text
No bid → best_bid() returns 0
No ask → best_ask() returns 0
```

Within the simulator, `0` is reserved as a sentinel for the absence of an available quote and is not used as a valid market price.

This convention is retained rather than introducing `std::optional<Price>` into the core quote API because doing so would unnecessarily propagate a representation change through the existing architecture.

---

## 7. Bid-Ask Spread

The spread is:

```text
Spread = Best Ask − Best Bid
```

When either side is unavailable, the existing `OrderBook` convention returns:

```text
Spread = 0
```

---

## 8. Adding an Order

When an order is added, its side determines the target side of the book.

```text
                    Order
                      |
            +---------+---------+
            |                   |
           BUY                SELL
            |                   |
          bids                asks
```

If the relevant price level already exists, the order is appended to the existing level.

If not, a new price level is created.

Orders are stored in insertion order within a price level so FIFO priority can be preserved.

---

## 9. Order Cancellation

Orders are removed using their `OrderId`.

The cancellation path is:

```text
cancel(order_id)

      ↓

Find OrderLocation in OrderMap

      ↓

Locate corresponding PriceLevel

      ↓

Remove order from price level

      ↓

Update total_quantity

      ↓

Remove OrderMap entry

      ↓

Update shifted indices

      ↓

Is price level empty?

 ├── YES → Remove price level
 └── NO  → Keep price level
```

The operation returns `true` when an order is successfully cancelled and `false` when the order does not exist or cannot be located.

---

## 10. Empty Price Levels

A price level must not remain in the book after its final order has been removed.

The same rule applies after execution.

When the final resting order at a price level is completely filled, the price level is removed.

This ensures the book represents currently available liquidity rather than historical price levels.

---

# Part II — Matching Engine

## 11. Matching Engine Overview

The matching engine processes an incoming order against the opposite side of the book.

The fundamental rule is:

```text
BUY  → matches against ASKS
SELL → matches against BIDS
```

Conceptually:

```text
Incoming Order

      ↓

Determine Side

      ↓

Find Opposite Side

      ↓

Check Price Crossing

      ↓

Match FIFO Orders

      ↓

Generate Trade(s)

      ↓

Update Quantities

      ↓

Remove Filled Orders / Levels

      ↓

Rest Remaining Quantity
```

Matching remains the responsibility of `OrderBook`.

The matching engine is not aware of:

```text
inventory
cash
P&L
portfolio value
risk statistics
```

Those are handled above the matching layer.

---

## 12. Trade

A `Trade` represents one executed transaction between an incoming order and a resting order.

The structure contains:

```text
Trade

├── incoming_order
├── resting_order
├── price
└── quantity
```

Conceptually:

```cpp
struct Trade {
    OrderId incoming_order;
    OrderId resting_order;
    Price price;
    Quantity quantity;
};
```

The trade intentionally does not store:

```text
incoming side
arrival midpoint
inventory information
```

The simulator supplies that contextual information to later analytical/accounting layers.

---

## 13. BUY Matching

For an incoming BUY order, the matching engine examines the ask side.

The lowest ask has highest execution priority.

The crossing condition is:

```text
incoming BUY price >= resting ASK price
```

Matching continues while the condition remains true.

Any remaining quantity becomes resting bid liquidity.

---

## 14. SELL Matching

For an incoming SELL order, the matching engine examines the bid side.

The highest bid has highest execution priority.

The crossing condition is:

```text
incoming SELL price <= resting BID price
```

Matching continues while the condition remains true.

Any remaining quantity becomes resting ask liquidity.

---

## 15. Price-Time Priority

The matching engine follows price-time priority.

Price priority:

```text
BUY  → lowest executable ASK first
SELL → highest executable BID first
```

Within a price level, FIFO priority is represented by order order inside the vector.

---

## 16. Full Fill

A full fill occurs when the incoming order's remaining quantity is less than or equal to the resting order's quantity.

If the incoming quantity exactly equals the resting quantity, both are fully consumed and the resting order is removed.

---

## 17. Partial Fill

A partial fill occurs when an incoming order is larger than available quantity at the current resting order.

Example:

```text
Resting SELL → 30
Incoming BUY  → 50
```

Execution:

```text
30
```

Remaining incoming quantity:

```text
20
```

Matching then continues.

---

## 18. Multiple Price Levels

An incoming order can consume liquidity across multiple price levels.

Example:

```text
ASKS

10000 → 20
10100 → 30
10200 → 40
```

Incoming:

```text
BUY @ 10200 × 60
```

Execution:

```text
20 @ 10000
30 @ 10100
10 @ 10200
```

This behavior directly supports the execution analysis introduced in Chapter 7.

---

## 19. Trade Generation

Every individual execution creates a `Trade`.

A single incoming order may therefore generate:

```text
Trade 1
Trade 2
Trade 3
...
```

The returned vector preserves execution order.

---

## 20. Order Quantity During Matching

The incoming order's quantity represents the remaining unfilled quantity.

```text
Initial Quantity
      ↓
Match
      ↓
Subtract Executed Quantity
      ↓
Remaining Quantity
      ↓
Continue Matching
```

When the remaining quantity reaches zero, matching stops.

Any positive remainder becomes resting liquidity.

---

## 21. Matching and Book State Updates

For a trade of quantity `Q`:

```text
Resting Quantity -= Q
```

and:

```text
PriceLevel Total Quantity -= Q
```

If the resting order becomes zero, it is removed.

If the price level becomes empty, it is removed.

The order book therefore remains synchronized with generated trades.

---

## 22. Crossing Versus Resting

An incoming order has two possible outcomes.

### Crossing Order

```text
Incoming Order
      ↓
Executable Liquidity Exists
      ↓
Matching
      ↓
Trade(s)
```

### Non-Crossing Order

```text
Incoming Order
      ↓
No Executable Liquidity
      ↓
No Trade
      ↓
Order Rests
```

# Part III — Order ID Tracking

## 23. Motivation for OrderMap

Without an auxiliary index, locating an order by `OrderId` would require scanning bid and ask price levels and their orders.

Chapter 3 introduces:

```text
OrderId
   ↓
OrderLocation
```

through:

```cpp
std::unordered_map<OrderId, OrderLocation>
```

The map provides average constant-time lookup under normal hash-table behavior.

The map indexes the actual order-book storage; it does not replace the storage.

---

## 24. OrderLocation

An `OrderLocation` identifies the physical location of a resting order.

It contains:

```text
OrderLocation

├── side
├── price
└── index
```

Conceptually:

```cpp
struct OrderLocation {
    Side side;
    Price price;
    std::size_t index;
};
```

---

## 25. OrderMap Structure

```text
OrderBook

├── bids
│   └── PriceLevels
│       └── Orders
│
├── asks
│   └── PriceLevels
│       └── Orders
│
└── OrderMap
    └── OrderId → OrderLocation
```

The actual `Order` remains inside its `PriceLevel`.

---

## 26. Why the Map Stores Location Rather Than Order Pointers

The book stores:

```cpp
std::vector<Order>
```

inside price levels.

The index therefore stores:

```text
OrderId
    ↓
Side + Price + Index
```

rather than making persistent pointers part of the ownership architecture.

Ownership remains:

```text
OrderBook
    owns PriceLevels
        which own Orders
```

The `OrderMap` is an auxiliary lookup structure.

---

## 27. Adding Orders to OrderMap

When an order becomes resting liquidity, the `OrderBook` inserts its location into the `OrderMap`.

An incoming order that becomes completely filled is never added as resting liquidity.

---

## 28. Removing Orders from OrderMap

When a resting order is cancelled or completely filled, its `OrderMap` entry is removed.

Vector erasure may shift later orders, so affected indices are updated.

---

## 29. Shifted Indices

The underlying order storage uses:

```cpp
std::vector<Order>
```

Erasing an order from the middle shifts later elements.

Therefore the corresponding `OrderMap` entries must remain synchronized.

---

## 30. OrderMap Invariant

The central invariant is:

```text
Every resting order in the book has exactly one OrderMap entry.

Every OrderMap entry corresponds to exactly one resting order.
```

---

## 31. Partial Fills and OrderMap

A partial fill changes quantity but not location:

```text
Partial Fill
    ↓
Quantity changes
    ↓
Location unchanged
    ↓
OrderMap unchanged
```

---

## 32. Full Fills and OrderMap

When a resting order is fully filled:

```text
Resting Quantity → 0
```

the order and its `OrderMap` entry are removed.

---

# Part IV — Order Lookup and Modification

## 33. Direct Order Lookup

Chapter 4 provides:

```cpp
Order* find_order(OrderId order_id);
```

The lookup path is:

```text
OrderId
   ↓
OrderMap::find()
   ↓
OrderLocation
   ↓
Select bids / asks
   ↓
Locate PriceLevel
   ↓
Access orders[index]
   ↓
Return Order*
```

The returned pointer is temporary access into vector-owned storage.

It must not be retained across operations capable of erasing or reallocating the underlying vector.

---

## 34. Order Modification / Replace

The public operation is:

```cpp
bool modify(
    OrderId order_id,
    Price new_price,
    Quantity new_quantity
);
```

The current logic is:

```text
modify()

    ↓

find_order()

    ↓

Does order exist?

 ├── NO → false
 │
 └── YES
      ↓
new_quantity == 0?
 │
 ├── YES → cancel()
 │
 └── NO
      ↓
Same price AND quantity decrease/equal?
 │
 ├── YES → modify in place
 │
 └── NO
      ↓
cancel(old)
      ↓
add(replacement)
      ↓
FIFO priority resets
```

---

## 35. FIFO Rules for Modification

### Same Price + Quantity Decrease

Modify in place.

FIFO is preserved.

### Same Price + Quantity Increase

Cancel and reinsert.

FIFO is lost.

### Price Change

Cancel and reinsert.

FIFO priority resets.

---

## 36. Quantity Zero as Cancellation

A modification with:

```text
new_quantity = 0
```

is treated as cancellation.

---

## 37. Order ID and Side Preservation

A replacement retains:

```text
Original OrderId
Original Side
```

Only the modified attributes change:

```text
Price
Quantity
```

---

## 38. OrderMap During Modification

In-place modification:

```text
Order
   ↓
Quantity updated
   ↓
Location unchanged
   ↓
OrderMap unchanged
```

Replacement:

```text
cancel()
   ↓
OrderMap entry removed
   ↓
add()
   ↓
New location created
   ↓
OrderMap entry recreated
```

```text

├── sequence
```

Field usage:

```text

CANCEL

→ order_id
→ new_price
→ new_quantity
```

---

## 40. Timestamp and Sequence Number

Each event contains:

```text
timestamp
sequence
```

The current model is:

```text
100   0
100   1
100   2

101   0
101   1

102   0
```

Validation rules:

```text
timestamp < current_time
    → reject

timestamp == current_time
    → sequence > last_sequence

timestamp > current_time
    → sequence == 0
```

Accepted events update:

```text
current_time
last_sequence
```

Rejected events do not advance simulator temporal state.

The timestamp unit is logical nanoseconds for the current simulator representation.

## 42. Simulator Event Dispatch

### ADD

For an accepted ADD event:

```text
ADD Event
   ↓
Validate event
   ↓
Capture incoming Side
   ↓
Capture arrival Midpoint
   ↓
Process order through OrderBook
   ↓
Generate Trade(s)
   ↓
Update Trade History
   ↓
Update InventoryModel from generated Trade(s)
```

The arrival midpoint is captured before matching:

```cpp
calculate_mid_price(order_book)
```

The side is stored before matching:

```text
OrderId → Side
```

The incoming order is then passed through:

```cpp
order_book.process_order()
```

Every generated trade is appended to:

```cpp
trades
```

and passed to:

```cpp
inventory_model.process_trade(
    trade,
    event.order.side
);
```

All trades generated by one incoming order therefore use the same incoming side.

### CANCEL

The simulator calls:

```cpp
order_book.cancel(order_id);
```

### MODIFY

The simulator calls:

```cpp
order_book.modify(
    order_id,
    new_price,
    new_quantity
);
```

The `OrderBook` remains responsible for book-state semantics.

## 54. Mid-Price

The mid-price is:

```text
Mid = (Best Bid + Best Ask) / 2
```

The result can fall between integer ticks:

```text
Best Bid = 10000
Best Ask = 10501

Mid = 10250.5
```

Therefore:

```cpp
using MidPrice = double;
```

When either side is unavailable:

```text
Mid = 0.0
```

---

```text

```

```text
Relative Spread
=
(Best Ask − Best Bid)

         Mid
```


# Part VII — Execution Analysis

## 66. Execution Analysis Overview

Chapter 7 introduces execution analysis above the simulation engine.

Chapter 6 asks:

Chapter 7 asks:

It does not perform matching.

It does not own orders.

It does not maintain another order book.

It does not maintain inventory state.

# Part VIII — Inventory / P&L / Risk

## 85. Inventory Model Overview

Chapter 8 introduces persistent inventory and accounting state above the matching engine.

The module is:

```text

```

with:


```text

        ↓

```

Unlike Metrics and Execution Analysis, `InventoryModel` is **stateful**.

Metrics and execution analysis derive values from existing state.

Inventory accounting maintains state over time.

---

## 86. Inventory Model State

The current persistent state is:

```text
InventoryModel

├── position
├── cash
├── avg_cost
└── realized_pnl
```

Conceptually:

```cpp
class InventoryModel {
private:
    Position position;
    Cash cash;

};
```

---

## 87. Inventory Types

Chapter 8 introduces:

```cpp
using Position = std::int64_t;
using AvgCost = double;
using Cash = double;
using Pnl = double;
```

The meanings are:

```text
Position
    signed inventory

AvgCost
    weighted-average cost basis

Cash
    accounting cash value

Pnl
    profit/loss value
```

---

## 88. Signed Inventory

Position is signed.

```text
position > 0
    → long

position = 0
    → flat

position < 0
    → short
```

Examples:

```text
+100
    → long 100

0
    → flat

-100
    → short 100
```

This allows the same state representation to support both long and short inventory.

---

## 89. Cash Accounting

For BUY:

```text
Cash decreases
```

For SELL:

```text
Cash increases
```

The accounting rule is:

```text
BUY
    cash -= price × quantity

SELL
    cash += price × quantity
```

Cash is an accounting value and is not represented using the `Price` type.

Quoted prices remain integer ticks.

---

## 90. Average Cost Basis

The model uses a weighted-average cost basis.

For a long position:

```text
New Average Cost
=
(old average × old quantity
 +
new price × new quantity)
--------------------------------
       new total quantity
```

For a short position, the same weighted-average concept is applied to the positive magnitude of the short inventory.

Example:

```text
SHORT 100 @ 10000
SHORT 100 @ 12000
```

gives:

```text
Average Cost
=
(100 × 10000 + 100 × 12000)
----------------------------
           200

= 11000
```

---

## 91. Average Cost Invariant

The model maintains the invariant:

```text
position == 0
    →
avg_cost == 0
```

When inventory becomes flat, the previous cost basis is discarded.

A subsequent position starts with a new cost basis.

---

## 92. Zero-Quantity Trade Invariant

A trade with:

```text
quantity == 0
```

is a no-op.

It must not change:

```text
position
cash
avg_cost
realized_pnl
```

This invariant is enforced before normal BUY/SELL accounting logic.

---

## 93. BUY Accounting

A BUY can represent three conceptual cases.

### Opening / Increasing Long

```text
position >= 0
```

BUY increases position.

```text
position += quantity
```

Cost basis is updated using weighted average.

---

### Closing Short

```text
position < 0
```

BUY first closes existing short inventory.

Realized P&L is:

```text
(avg_cost − buy_price) × closed_quantity
```

---

### Short → Long Crossing

If the BUY quantity exceeds the existing short quantity:

```text
Existing Short
       ↓
Close Short
       ↓
Remaining BUY Quantity
       ↓
Open New Long
```

The remaining long quantity receives:

```text
avg_cost = crossing trade price
```

---

## 94. SELL Accounting

A SELL can represent three conceptual cases.

### Opening / Increasing Short

```text
position <= 0
```

SELL increases short inventory.

```text
position -= quantity
```

Weighted-average cost is updated using the positive magnitude of the short position.

---

### Closing Long

```text
position > 0
```

SELL first closes existing long inventory.

Realized P&L is:

```text
(sell_price − avg_cost) × closed_quantity
```

---

### Long → Short Crossing

If the SELL quantity exceeds the existing long quantity:

```text
Existing Long
       ↓
Close Long
       ↓
Remaining SELL Quantity
       ↓
Open New Short
```

The remaining short quantity receives:

```text
avg_cost = crossing trade price
```

---

## 95. Long → Short Crossing

Example:

```text
BUY 100 @ 10000
SELL 150 @ 12000
```

Conceptually:

```text
100 units
    → close long

50 units
    → open short
```

Realized P&L:

```text
100 × (12000 − 10000)
=
200000
```

Final state:

```text
position = -50
avg_cost = 12000
```

Cash is still updated using the complete 150-unit SELL:

```text
cash += 150 × 12000
```

The closing/opening split affects inventory and P&L classification, not the cash settlement of the actual trade.

---

## 96. Short → Long Crossing

Example:

```text
SELL 100 @ 12000
BUY 150 @ 10000
```

Conceptually:

```text
100 units
    → close short

50 units
    → open long
```

Realized P&L:

```text
100 × (12000 − 10000)
=
200000
```

Final state:

```text
position = +50
avg_cost = 10000
```

Cash is updated using the complete 150-unit BUY.

---

## 97. Realized P&L

Realized P&L is persistent state.

It changes only when existing inventory is closed.

Long closure:

```text
(price − avg_cost) × quantity
```

Short closure:

```text
(avg_cost − price) × quantity
```

Opening inventory does not create realized P&L.

---

## 98. Unrealized P&L

Unrealized P&L is derived from current inventory and a mark price.

The current formula is:

```text
Unrealized P&L
=
position × (mark_price − avg_cost)
```

The signed position makes the same formula work for both long and short inventory.

For long:

```text
position > 0
```

For short:

```text
position < 0
```

Unrealized P&L is not stored persistently.

It is calculated when requested.

---

## 99. Mark Price

The inventory model does not own a market-data source.

The simulator or application obtains the current mark using the existing Chapter 6 function:

```cpp
calculate_mid_price(order_book)
```

The valuation flow is:

```text
OrderBook
    ↓
calculate_mid_price()
    ↓
Mark Price
    ↓
InventoryModel valuation
```

No duplicate midpoint calculation is introduced.

No stored mark price is required.

---

## 100. Portfolio Value

Portfolio value is:

```text
Portfolio Value
=
Cash + Position × Mark Price
```

This is an accounting identity based on marked inventory.

It is not stored.

It is derived when requested.

---

## 101. Total P&L

The total P&L relationship is:

```text
Total P&L
=
Realized P&L
+
Unrealized P&L
```

Under the current accounting model, this is equivalent to:

```text
Portfolio Value − Initial Cash
```

assuming the inventory model has processed the complete trade history from the same initial state.

---

## 102. Inventory Exposure

Inventory exposure measures the absolute marked size of inventory:

```text
Inventory Exposure
=
|Position| × Mark Price
```

Therefore:

```text
+100 @ 11000
    → exposure = 1,100,000

-100 @ 11000
    → exposure = 1,100,000
```

Exposure is directional-neutral.

A short position does not produce negative exposure.

---

## 103. Inventory Limits

Inventory limits are intentionally not part of the matching engine.

The current chapter treats inventory limits as a future control/measurement concept rather than making them an admission gateway inside `OrderBook`.

Therefore:

```text
OrderBook
    → matching semantics

InventoryModel
    → accounting state

Future risk/control layer
    → policy constraints
```

This avoids coupling portfolio policy to the core matching engine.

# Part XV — Current Performance Model

## 137. Current Performance Model

The current vector-based implementation is designed primarily for correctness and conceptual clarity.

It is not yet the final high-performance architecture.

Current characteristics include:

```text
Price-level search
    → linear in number of levels

Order insertion into level
    → vector append

Order removal
    → vector erase + shifted-index updates

Order ID lookup
    → average O(1) through unordered_map

Direct order resolution
    → map lookup + price-level search

Matching
    → traversal of price levels and orders

FIFO-preserving modification
    → in-place mutation

Priority-changing modification
    → cancel + reinsert

Event storage
    → vector append

Event processing
    → sequential event traversal

Bid / ask depth
    → traversal of price levels

Trade count
    → O(1) from vector size

Trade volume
    → linear in trade-history length

Trade grouping
    → average O(n) over trade history

Execution result calculation
    → linear in grouped trade count

Complete execution analysis
    → dominated by trade aggregation and calculation

Inventory trade processing
    → O(1) state update per Trade

Inventory valuation
    → O(1)

Complete market metrics
    → dominated by depth and trade-volume traversal
```

The metrics, execution, and inventory valuation layers do not introduce mutable caches for premature optimization.

Future optimization decisions will be measured rather than assumed.

The objective is:

```text

      +

      +

Correct Modification Semantics

      +

Correct Event Processing

      +

Correct Market Metrics

      +

Reliable Simulation Core
```

The system maintains explicit ownership boundaries:

```text
OrderBook
    → market-state source of truth
```


```text

```



```text

```

No analytical module maintains a second copy of the order book.

---

## 162. Explicit Invariants

The principal invariants established so far are:

### OrderMap invariant

```text
Every resting order
    ↔
Exactly one OrderMap entry
```

### FIFO invariant

```text
Orders at the same price
    →
Stored and matched in queue order
```

### Event invariant

```text
Accepted events
    →
Follow timestamp / sequence ordering
```

### Metrics invariant

```text
Metric calculations
    →
Do not mutate source state
```

### Execution-reference invariant

```text
Arrival reference
    →
Captured before matching
```

### Execution grouping invariant

```text
Each generated Trade
    →
Belongs to exactly one incoming OrderId group
```

### Execution-result invariant

```text
Each incoming OrderId with generated trades
    →
Produces exactly one ExecutionResult
```

### Inventory state invariant

```text
position == 0
    →
avg_cost == 0
```

### Zero-quantity invariant

```text
trade.quantity == 0
    →
Inventory state unchanged
```

### Portfolio accounting invariant

```text
Portfolio Value
=
Initial Cash + Total P&L
```

under the current complete-history model.

---

## 163. Measured Optimization

Future changes should follow:

```text
Measure

   ↓

Profile

   ↓

Find bottleneck

   ↓

Change implementation

   ↓

Benchmark

   ↓

Verify correctness
```

No major container redesign should be introduced merely because a theoretical complexity improvement appears attractive.

The current vector-based design remains the established architecture unless later benchmarking demonstrates a real bottleneck.
